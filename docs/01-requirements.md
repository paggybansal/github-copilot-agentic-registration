## 1. Scope

In scope:

- Displaying the `/register` page with Full Name, Email, Password, Confirm Password and a
  Register button.
- Creating exactly one user account per successful submission.
- Hashing passwords with Werkzeug before storage.
- Validating required fields, field lengths, email format, full-name character policy,
  password strength rules and password confirmation.
- Enforcing case-insensitive email uniqueness in the application and in SQLite.
- Redirecting to a dedicated success page after successful registration (POST-Redirect-GET).
- CSRF protection for the registration POST request using Flask-WTF.
- Safe handling of unexpected database failures with rollback and a generic user message.

### 1.1 Out of scope

- Login and logout
- Email verification
- Password reset
- CAPTCHA
- Social login
- User profile
- Administration
- Production deployment

## 2. Glossary

| Term | Meaning |
|---|---|
| Normalized email | An email address after leading/trailing whitespace trimming and lowercasing |
| Trimmed value | A value after leading and trailing whitespace removal |
| Generic database-failure message | `Registration could not be completed. Please try again` |
| Duplicate-email message | `An account with this email already exists` |
| Success page | A dedicated page displayed only after a successful POST-Redirect-GET, showing `Registration successful` |

## 3. Functional Requirements

| ID | Requirement | Source AC | Priority | Acceptance test |
|---|---|---|---|---|
| FR-1 | The application shall display Full Name, Email, Password, Confirm Password and a Register button on a GET request to `/register`. | AC1 | Must | Verify that GET `/register` returns HTTP 200 and the response contains all five elements. |
| FR-2 | The application shall create exactly one account when all submitted fields are valid, the email is not already registered, and the passwords match. | AC2 | Must | Verify that one row exists in the `users` table after a valid POST. |
| FR-3 | The application shall store only a password hash generated by Werkzeug `generate_password_hash` and shall never store the submitted password in plain text. | AC2 | Must | Verify the stored value differs from the submitted password and `check_password_hash` succeeds against it. |
| FR-4 | The application shall redirect (POST-Redirect-GET) to a dedicated success page after successful registration, and that page shall display only `Registration successful` without submitted name, email, password or password hash. | AC2, Clarification 4 | Must | Verify the POST response is a redirect and the followed GET response body contains only the success message and not submitted data. |
| FR-5 | The application shall reject a submission with one or more empty required fields (Full Name, Email, Password, Confirm Password after trimming), create no account, and display a field-specific validation message for each missing field. | AC3 | Must | Verify POST with an empty field returns HTTP 200, no new account row exists, and a message is shown per missing field. |
| FR-6 | On any validation, duplicate-email, or database-error failure, the application shall retain the submitted Full Name and Email values in the re-rendered form and shall always clear Password and Confirm Password. | AC3, Clarification 8 | Must | Verify the re-rendered form HTML contains the submitted name/email and empty password fields after each failure type. |
| FR-7 | The application shall reject a submission whose Email does not match a valid email format and shall display `Enter a valid email address`, creating no account. | AC4 | Must | Verify POST with an invalid email returns HTTP 200, shows the exact message, and no account row exists. |
| FR-8 | The application shall reject a submission where Password and Confirm Password differ and shall display `Passwords do not match`, creating no account. | AC5 | Must | Verify POST with mismatched passwords returns HTTP 200, shows the exact message, and no account row exists. |
| FR-9 | The application shall reject a Password that does not contain at least 8 characters, at least one uppercase letter, at least one lowercase letter and at least one number, displaying a clear validation message, creating no account. | AC6 | Must | Verify POST with a password violating each individual rule is rejected with a message and no account row exists. |
| FR-10 | The application shall reject a submission whose normalized (trimmed, lowercased) email matches an existing account's normalized email, regardless of original letter casing, displaying `An account with this email already exists`, creating no second account. | AC7 | Must | Verify POST with an existing email in different casing returns HTTP 200, shows the exact message, and exactly one account row exists for that email. |
| FR-11 | On an unexpected database error during account creation, the application shall roll back the transaction, create no partial account, and display `Registration could not be completed. Please try again` without exposing passwords, hashes, SQL, or database details. | AC8 | Must | Verify a simulated database failure leaves zero new rows, shows the exact generic message, and the response/logs contain no password, hash, SQL text or database path. |
| FR-12 | The application shall trim leading and trailing whitespace from Full Name and Email before validation, and shall lowercase the trimmed Email before duplicate lookup and storage; Password and Confirm Password shall never be trimmed or otherwise modified. | Clarification 2 | Must | Verify a submission with surrounding whitespace in name/email is normalized before validation and storage, and that password values are stored/compared unmodified. |
| FR-13 | The application shall reject a Full Name that is empty after trimming, that is whitespace-only, or that contains Unicode control characters, while allowing Unicode letters and normal punctuation. | Clarification 3 | Must | Verify a whitespace-only name and a name containing a control character are rejected; verify a legitimate international name with punctuation is accepted. |
| FR-14 | The application shall enforce a maximum of 100 characters for the trimmed Full Name, 254 characters for the trimmed Email, and 128 characters for Password and Confirm Password, with a minimum of 8 characters for Password. | Clarification 1 | Must | Verify values at the exact limit are accepted and values at limit+1 are rejected for each field. |
| FR-15 | The application shall require a valid CSRF token, generated by Flask-WTF, on every registration POST request in the real application configuration. | Clarification 5 | Must | Verify a POST without a CSRF token and a POST with an invalid CSRF token are both rejected; verify a POST with a valid token succeeds. |
| FR-16 | The application shall render all user-submitted values (including Full Name) through Jinja's default auto-escaping and shall never apply `|safe` or unescaped HTML construction to submitted values. | Clarification 3 | Must | Verify a Full Name containing a script-shaped string is rendered as escaped text and does not execute in a browser. |

## 5. Error and Edge Cases

| ID | Case | Expected behavior | Related FR |
|---|---|---|---|
| EC-1 | Full Name is empty after trimming | Rejected with a field-specific message; no account created | FR-5, FR-13 |
| EC-2 | Full Name is whitespace-only | Rejected; no account created | FR-13 |
| EC-3 | Full Name contains a Unicode control character | Rejected; no account created | FR-13 |
| EC-4 | Full Name exactly 100 characters (post-trim) | Accepted | FR-14 |
| EC-5 | Full Name 101 characters (post-trim) | Rejected with a length-related message | FR-14 |
| EC-6 | Email exactly 254 characters (post-trim) | Accepted (subject to format validity) | FR-14 |
| EC-7 | Email 255 characters (post-trim) | Rejected with a length-related message | FR-14 |
| EC-8 | Password exactly 8 characters meeting all strength rules | Accepted | FR-14 |
| EC-9 | Password exactly 128 characters meeting all strength rules | Accepted | FR-14 |
| EC-10 | Password 129 characters | Rejected with a length-related message | FR-14 |
| EC-11 | Password missing an uppercase, lowercase, or number (tested individually) | Rejected with a clear password-rule message | FR-9 |
| EC-12 | Email in a different letter case than an existing account | Rejected as duplicate; no second account created | FR-10 |
| EC-13 | Email with surrounding whitespace that normalizes to an existing account's email | Rejected as duplicate | FR-10, FR-12 |
| EC-14 | Simulated SQLite failure during insert | Transaction rolled back; no partial account; generic message shown | FR-11 |
| EC-15 | Registration POST without a CSRF token | Request rejected by Flask-WTF; no account created | FR-15 |
| EC-16 | Registration POST with an invalid CSRF token | Request rejected by Flask-WTF; no account created | FR-15 |
| EC-17 | Full Name containing a script-shaped value (e.g. `<script>alert("registration-xss-test")</script>`) | Value is treated as data, escaped on any render, does not execute | FR-16, NFR-3 |
| EC-18 | SQL-injection-shaped input in Email or Full Name (e.g. `' OR '1'='1`) | Treated as literal data via parameterized SQL; no injection effect | FR-2, FR-10 |
| EC-19 | Refreshing the success page after redirect | Does not resubmit the form or create a duplicate account | FR-4 |

## 6. Data-Validation Rules

| Field | Rule |
|---|---|
| Full Name | Trim whitespace; reject if empty after trim; reject whitespace-only; reject Unicode control characters; allow Unicode letters and normal punctuation; max 100 characters after trim |
| Email | Trim whitespace; lowercase after trim; must match a valid email format; max 254 characters after trim; normalized value used for both duplicate lookup and storage |
| Password | No trimming or modification; min 8, max 128 characters; must contain at least one uppercase letter, one lowercase letter, and one digit |
| Confirm Password | No trimming or modification; max 128 characters; must exactly equal Password |

## 7. Security Requirements

| ID | Requirement |
|---|---|
| SEC-1 | Passwords shall be hashed using Werkzeug `generate_password_hash` and verified using `check_password_hash`; no manual cryptography. |
| SEC-2 | Email uniqueness shall be enforced both by an application-level lookup on the normalized email and by a SQLite `UNIQUE` constraint on the `email` column. |
| SEC-3 | All SQL statements shall use parameterized queries; no f-strings, `%` formatting, `.format()`, or string concatenation with user input. |
| SEC-4 | Every registration POST request shall require a valid Flask-WTF CSRF token in the real application configuration; CSRF may be disabled only through explicit test configuration. |
| SEC-5 | Jinja auto-escaping shall remain enabled for all templates; `|safe` and `Markup` shall not be applied to submitted values. |
| SEC-6 | Database failures shall trigger a rollback and shall return only the generic message `Registration could not be completed. Please try again`, with no password, hash, SQL, or database detail exposed in the response or logs. |
| SEC-7 | Password and Confirm Password fields shall never be repopulated after any failure. |
| SEC-8 | Secrets (Flask secret key, configuration) shall be supplied via environment variables or injected configuration; `.env`, private keys, credentials, and SQLite database files shall never be committed. |

## 8. Clarification Register

|---|---|---|
| 1 | Maximum field lengths? | Full Name ≤100 (post-trim), Email ≤254 (post-trim), Password 8–128, Confirm Password same max; boundary tests at limit and limit+1 |
| 2 | Whitespace normalization? | Trim Full Name/Email before validation; lowercase Email after trim; reject Full Name empty after trim; never trim/modify Password or Confirm Password |

### Additional confirmed decisions

- Validation errors return HTTP 200 with the form re-rendered and field-specific messages visible.
- Missing or invalid CSRF submissions are handled by Flask-WTF's normal rejection response.
- Unexpected database failure message: `Registration could not be completed. Please try again`.
- Duplicate email message: `An account with this email already exists`.
- No production code, architecture, or implementation plan was created during Step 1.

## 9. Assumptions

- Flask-WTF is approved as the one new runtime dependency for this story (per Clarification 5); no other new dependency is approved.
- "Valid email format" means a standard syntactic check (e.g. local-part@domain with at least one dot in the domain); exact regex/library choice is an architecture-stage decision.
- The SQLite `users` table schema (columns, types, constraints) is an architecture-stage decision; this document only requires that `email` be enforced unique.
- The Selenium UI test environment provides a locally installed, headless-capable Chrome; CI environment specifics are an implementation/verification-stage concern.
